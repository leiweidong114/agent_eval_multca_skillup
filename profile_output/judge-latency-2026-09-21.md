# 历史会话指标 Judge 耗时分析（2026-09-21）

## 测量范围与方法

- 数据来源：本机 `backend/evaluation_results/_judge/index.jsonl` 的最近两天审计摘要；只读取目的、模型、状态、时间和错误，不读取对话正文或密钥。
- 测量的是 Judge 调用的墙钟时间，不是 CPU 时间。数据库读取、Java 接口和浏览器渲染不包含在以下模型调用时长中。
- 当前统计的模型均为 `oc/nemotron-3.5-lightning`。这是本机历史样本，不代表内网模型的速度。

| 调用 | 成功样本 | 中位耗时 | P90 | 最长 |
| --- | ---: | ---: | ---: | ---: |
| 第一条 Prompt 任务分类 | 39 | 35.8 秒 | 186.4 秒 | 424.4 秒 |
| 完整会话指标 Judge | 48 | 85.8 秒 | 220.1 秒 | 453.0 秒 |
| 原理图质量解释 Judge | 2 | 41.9 秒 | 41.9 秒 | 56.0 秒 |

同一会话有分类和指标 Judge 成功记录的 25 个样本中，两次调用耗时之和的中位数为 **180.6 秒**；若两次调用完全重叠，二者较慢者的中位数为 **128.4 秒**，潜在重叠节省时间的中位数为 **42.0 秒**。这是根据历史耗时估计的理论上限，并非优化后的实测结果；实际还受 MongoDB 查询、网关并发能力、请求排队和多分片 Judge 影响。

失败样本中有 192 条包含 HTTP 530，另有 27 条空内容/非 JSON、6 条网络超时或断开、3 条格式错误。并发优化无法修复这些网关/模型错误；若 530 随并发上升，应在 `.env` 设置 `SESSION_METRIC_JUDGE_PARALLELISM=1`。

## 已实施的优化

规则指标完成后，提前在后台开始完整会话 Judge，同时主 Worker 进行第一条 Prompt 分类和 MongoDB 查询。两个 Judge 结果仍分别验证和保存；第六步等待后台结果后才合并并持久化最终指标。全局最多允许 2 个历史指标 Judge 请求同时进行，避免批量会话无限并发。前端实时计时仍从各 Judge 实际开始事件起算。

## 验证与限制

- 并发单元测试以相互等待的两个模拟调用验证分类和完整会话 Judge 确实重叠，不用真实模型配额。
- 本次未对生产 LiteLLM 发送额外推理请求；真实端到端提速幅度须在部署后以页面计时和 Judge 审计记录复测。
- 质量解释 Judge 只有在查询到对应原始记录时才运行。完整会话 Judge 分片内部仍依次调用，超长会话仍可能慢。
