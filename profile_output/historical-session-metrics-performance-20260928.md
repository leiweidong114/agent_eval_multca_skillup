# 历史会话指标计算性能分析（2026-09-28）

## 结论

当前主要瓶颈不是 Python 规则计算，而是 Judge LLM 推理和每条会话完成后的全量累计指标刷新。

实测会话 `b8ad8d49-d362-4462-8318-174fb712e2e6` 在任务分类 Judge、会话 Judge 均关闭，仅保留四类质量指标 Judge 时，总耗时约 32.74 秒：

| 阶段 | 实测耗时 | 总耗时占比 | 说明 |
|---|---:|---:|---|
| LiteLLM PostgreSQL 会话读取 | 0.46 秒 | 1.4% | 读取完整会话，样本只有 1 轮 |
| 确定性规则计算 | 约 0.001 秒 | <0.1% | 规则分类、工具、脚本、Skill、错误和重试统计 |
| Java/MongoDB 原始记录读取与规则提取 | 约 0.11 秒 | 0.3% | 读取并解析 3 条质量记录 |
| 四类质量指标 Judge | 27.50 秒 | 84.0% | `glm-4.5-air`，4106 输入 tokens、2328 输出 tokens |
| 单会话指标写入及写后回读 | 0.31 秒 | 1.0% | 包含替换旧记录、插入和验证 |
| 全局累计指标刷新 | 4.35 秒 | 13.3% | 全量分页扫描、重新汇总、删除旧汇总、插入并回读 |

## 当前执行关系

1. PostgreSQL 读取完整会话。
2. 本地确定性规则计算。
3. 如果开启会话 Judge，将它提交到单线程 Judge executor 后台执行。
4. 如果开启任务分类 Judge，主 Worker 同步等待分类完成。
5. 查询 MongoDB 原始质量记录并运行本地提取。
6. 四类质量指标 Judge 在主 Worker 中同步运行。
7. 等待后台会话 Judge 完成。
8. 写入单会话指标，并写后回读。
9. 全量扫描所有历史指标，刷新唯一汇总记录。
10. 再次替换指标记录，以保存最终过程轨迹。

任务分类与会话 Judge 已有并行重叠测试，但质量指标 Judge 必须等任务分类结束才启动。并发槽默认最多 2 个；会话 Judge executor 只有 1 个线程。单个会话 Judge 按约 42,000 字符分片，多个分片当前逐个串行调用模型。

## 优化优先级

### P0：缩短 Judge 输出，不关闭模型推理

- 四类质量率已经由计数规则精确计算，Judge 只需返回“通过/不一致项/中文原因”，不应重新输出大段证据。
- 输入只发送规则值、计数和每项最短证据片段，不再发送每条最多 12,000 字符的完整 `resultText`。
- 为任务分类、质量审计、会话 Judge 分别设置较小的输出 token 上限。
- 预期：质量 Judge 的 2328 输出 tokens 可压缩至约 300-600，通常可把 27.5 秒降至约 6-12 秒；实际结果取决于上游模型吞吐。

### P0：累计指标改为增量更新

当前每完成一个会话就全量读取整个集合。样本已有 456 个指标会话，单次刷新耗时 4.35 秒；批量计算 100 条时会重复全量扫描 100 次。

保持“每算完一条立即更新汇总”的语义，可以：

- 读取该 Session 旧指标和新指标，计算计数差量；
- 通过 Java/MongoDB 原子更新唯一的“汇总结果”文档；
- 定时执行一次全量校准，防止历史异常累积。

这样每条会话的汇总刷新可由 O(全部历史记录) 降为 O(1)。

### P1：合并冗余 Judge 任务

会话指标 Judge 已经输出 `task_type`，可直接作为 LLM 任务分类结果，避免单独再调用一次任务分类模型。仍然属于 LLM 分类，并未关闭模型推理。短会话实测可直接节省约 7.97 秒。

如果必须保留独立分类调用，则应在会话加载后同时启动：任务分类、质量数据查询/质量 Judge、会话 Judge；不要让质量 Judge 等分类完成后才开始。

### P1：减少 MongoDB 往返次数

同一 Session 当前会发生多次重复查询：合理性查询、质量记录查询、旧指标查询、写后回读、过程轨迹刷新查询。建议：

- 首次查询一次拿到同一 Session 的全部记录，在流水线内复用；
- Java 增加原子 replace/upsert 接口，返回新 `_id` 和保存后的核心字段；
- 最终过程轨迹与指标一次写入，避免成功后再 delete + insert 一次；
- 保留必要的写后验证，但使用按 `_id` 查询，而不是再次拉取该 Session 全部记录。

### P1：长会话分片并行

会话 Judge 每约 42,000 字符产生一个分片，当前按分片串行。可在可配置并发上限内并行处理分片，然后使用现有确定性 reducer 合并。若 4 个分片每个约 24 秒，串行约 96 秒，并发 2 可接近 48 秒。

需要同时限制全局 LiteLLM 并发，避免 429。

### P2：连接池和索引

- 使用长期 `httpx.Client` 复用 LiteLLM 和 Java API 的 TCP 连接。
- PostgreSQL 对会话 ID、`end_user`、时间字段建立匹配查询模式的索引。
- MongoDB/Java 查询对 `sessionId + checkType + createTime` 建复合索引，对 `_id` 精确查询。

这些措施主要优化 0.2-0.8 秒级的数据访问，不会替代 P0 的 Judge 和累计汇总优化。

## 超时和失败放大因素

每次 Judge 请求默认超时 120 秒，可对 429/5xx/网络错误重试 4 次，并带退避；JSON mode 被拒绝或返回空内容时还会不带 `response_format` 再请求一次。因此异常情况下单个 Judge 可能从几十秒放大到数分钟。建议按任务类型配置更短超时，并对明确的额度耗尽错误快速失败。
